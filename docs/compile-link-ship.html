MODULE 01~4 hours

What compiling really means

Goals
  • Build a multi-file program by hand with g++, step by step.
  • Tell a compiler error from a linker error at a glance.
  • Know what headers, object files, static and shared libraries are, and how Windows finds a DLL.

"Compiling" is really four programs run in a row, shown at the top of this page. IDEs hide them, which is why build errors feel mysterious. Run them yourself once and they stop being mysterious.

One file, four steps

cpp · hello.cpp
#include <iostream>

int main()
{
    std::cout << "Hello from C++\n";
    return 0;
}
powershell
g++ -E hello.cpp -o hello.i     # 1. preprocess: #include pasted in (open it: ~30,000 lines!)
g++ -S hello.cpp -o hello.s     # 2. compile to assembly
g++ -c hello.cpp -o hello.o     # 3. assemble to an object file (machine code + symbol table)
g++ hello.o -o hello.exe        # 4. link: resolve symbols, add the C++ runtime, write the .exe
.\hello.exe

Normally you write g++ hello.cpp -o hello.exe and all four happen at once. The important split is between steps 1–3, which work on one file at a time (a translation unit), and step 4, which sees everything.

Several files: declarations and definitions

A declaration says something exists (“there is a function add taking two ints”). A definition provides it. Headers carry declarations so every .cpp can call the function; exactly one .cpp carries the definition.

cpp · mathx.h
#pragma once            // include this header at most once per translation unit

int add(int a, int b);  // declaration only
cpp · mathx.cpp
#include "mathx.h"

int add(int a, int b) { return a + b; }   // the one definition
cpp · main.cpp
#include <iostream>
#include "mathx.h"

int main() { std::cout << add(2, 3) << '\n'; }
powershell
g++ -c mathx.cpp -o mathx.o
g++ -c main.cpp  -o main.o
g++ main.o mathx.o -o app.exe     # works

g++ main.o -o app.exe             # forget mathx.o and the LINKER complains:
# undefined reference to `add(int, int)'

main.cpp compiled fine on its own because the header promised add exists. Only the linker discovered nobody delivered on that promise. Look inside the object files:

powershell
nm mathx.o      # T _Z3addii   -> "T" = defined here (in the Text section)
nm main.o       # U _Z3addii   -> "U" = used here, defined somewhere else
nm -C main.o    # -C demangles: U add(int, int)

_Z3addii is the mangled name: C++ encodes parameter types into symbol names so overloads like add(int,int) and add(double,double) can coexist. That detail returns in Module 09 when you call C++ from other languages.

# static: an archive of .o files
ar rcs libmathx.a mathx.o
g++ main.o -L. -lmathx -o app.exe          # -L = where to look, -l = which lib (lib*.a)

# shared
g++ -shared mathx.o -o mathx.dll -Wl,--out-implib,libmathx.dll.a
g++ main.o -L. -lmathx -o app.exe          # now app.exe needs mathx.dll at runtime

Windows looks for DLLs in the folder of the .exe, then the system folders, then every folder on PATH. That is why a Qt program runs from Qt Creator (Qt's bin is on its PATH) but fails with “Qt6Core.dll was not found” when double-clicked, until you deploy the DLLs next to it (Module 11). macOS instead records an install path such as @rpath/QtCore.framework inside the binary.

Try it
  1. Build the three-file program by hand. Then add a second definition of add in main.cpp and read the “multiple definition” error. Which step produced it?
  2. Delete #pragma once, include mathx.h twice in main.cpp, and add a struct Point { int x, y; }; to the header. Read the “redefinition” error. Which step produced that one?
  3. Make mathx a DLL, run app.exe, then move mathx.dll to another folder and run it again.
A message says undefined reference to `Widget::paint()'. Is the problem in your header, or in your build?

In the build. “Undefined reference” is the linker: something was declared and used, but no object file or library given to the linker defines it. Either the .cpp with the definition isn't being compiled/linked, or a library is missing from the link line (in CMake: missing from target_link_libraries).

Why can a header contain a class definition but not a normal function definition?

Every .cpp that includes the header gets its own copy. Class definitions (and inline functions, templates, functions defined inside a class body) are allowed to appear in many translation units as long as they're identical. A normal function definition would appear in several object files and the linker would report “multiple definition”. Mark such functions inline or move them to a .cpp.

MODULE 02~2 weeks

The C++ you actually need

Goals
  • Write classes that own resources safely (RAII) without manual delete.
  • Choose between values, references, pointers and smart pointers.
  • Use lambdas, the standard containers, std::optional and enum class fluently.

C++ is huge; app code uses a well-defined subset. For depth, work through learncpp.com chapters 1–21 alongside this module and keep cppreference.com open as the reference.

Ownership is the central idea

In C you remember to fclose and free. In C++ an object's destructor runs automatically when it goes out of scope, so you tie every resource to an object. This is called RAII (resource acquisition is initialisation), and it makes leaks and double-frees disappear even when errors or early returns happen.

cpp
#include <cstdio>
#include <stdexcept>
#include <string>

class File {
public:
    explicit File(const std::string &path) : m_f(std::fopen(path.c_str(), "rb"))
    {
        if (!m_f) throw std::runtime_error("cannot open " + path);
    }
    ~File() { std::fclose(m_f); }           // always runs, even on exceptions

    File(const File &) = delete;            // one owner: no copies...
    File &operator=(const File &) = delete;

    std::FILE *get() const { return m_f; }

private:
    std::FILE *m_f;
};

void readHeader(const std::string &path)
{
    File f(path);                           // opened here
    char magic[4];
    if (std::fread(magic, 1, 4, f.get()) != 4)
        return;                             // closed here...
    // ...
}                                           // ...or here. Never leaked.

The everyday toolkit

cpp
#include <algorithm>
#include <map>
#include <optional>
#include <string>
#include <vector>

enum class Status { Queued, Active, Done, Failed };   // scoped: write Status::Done

struct Transfer {
    std::string name;
    long long size = 0;            // default member initialisers
    Status status = Status::Queued;
};

std::optional<Transfer> findByName(const std::vector<Transfer> &list, const std::string &name)
{
    auto it = std::find_if(list.begin(), list.end(),
                           [&](const Transfer &t) { return t.name == name; });   // lambda
    if (it == list.end())
        return std::nullopt;
    return *it;
}

int main()
{
    std::vector<Transfer> queue{{"photo.jpg", 2'400'000}, {"notes.md", 1234}};
    queue.push_back({"song.mp3", 4'100'000});

    long long total = 0;
    for (const auto &t : queue)    // range-for; auto deduces Transfer
        total += t.size;

    std::map<std::string, int> counts;
    counts["jpg"]++;

    if (auto t = findByName(queue, "notes.md"))
        t->status = Status::Done;     // modifies the copy in t, not the vector

    for (auto &[ext, n] : counts) { /* structured bindings */ }
}

Lambdas and captures

Lambdas are everywhere in Qt code (button clicks, network replies). The capture list decides what the lambda can see:

  • [x] copies x now; [&x] refers to x (it must still exist when the lambda runs).
  • [this] lets you use members; the object must outlive the lambda.
  • For callbacks that run later (network, timers), capture by value or capture this with a guard. Capturing a local by reference in a delayed callback is the classic crash.

Move semantics in one paragraph

Copying a std::vector of a million items copies a million items. Moving it just steals the pointer inside. The compiler moves automatically when returning local variables and when the source is a temporary; write std::move(x) when you're done with x and want to hand it over. After a move, x is valid but unspecified: only assign to it or destroy it.

Try it
  1. Write a console “transfer queue” program: read file paths from the command line (argv), store them in a std::vector<Transfer> with their sizes (std::filesystem::file_size), sort by size with std::sort and a lambda, and print a table.
  2. Add a class Logger that opens a file in its constructor and closes it in its destructor. Prove the destructor runs by printing from it, including when you throw in the middle of main and catch it.
A function takes std::string name. Should it be const std::string &name?

If it only reads the string, yes: passing by const reference avoids a copy. If the function stores the string somewhere (for example in a member), taking it by value and then std::move-ing it into the member is the modern idiom.

CMake: describing a build

Goals
  • Write a CMakeLists.txt for an app split into a library and an executable.
  • Configure, build and install from the terminal, and open the same project in Qt Creator.
  • Understand PUBLIC / PRIVATE and why modern CMake is “target-based”.

Typing g++ lines doesn't scale past a handful of files or one platform. CMake is a description of what to build; it then generates the actual build system (Ninja, Visual Studio, Xcode). The same CMakeLists.txt builds Ferry on Windows and macOS.

cmake · CMakeLists.txt
cmake_minimum_required(VERSION 3.21)
project(Notes VERSION 0.1 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# A library target: the logic, with no user interface
add_library(notes_core STATIC
    src/core/Note.h  src/core/Note.cpp
    src/core/Store.h src/core/Store.cpp)
target_include_directories(notes_core PUBLIC src)          # users of notes_core also get -I src
target_compile_options(notes_core PRIVATE -Wall -Wextra)  # only for compiling notes_core itself

# An executable target that uses the library
add_executable(notes src/main.cpp)
target_link_libraries(notes PRIVATE notes_core)
powershell
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug   # configure: read CMakeLists, write build/
cmake --build build                                     # build (runs ninja)
.\build\notes.exe
cmake --build build --target clean                      # start over (or delete build/)

Keep the build folder outside your source tree (or ignored by git). You can have several at once: build-debug, build-release.

PUBLIC, PRIVATE, INTERFACE

Every setting attached to a target says who needs it:

KeywordUsed to build this targetPassed on to targets that link it
PRIVATEyesno
PUBLICyesyes
INTERFACEnoyes

Rule of thumb: if a library's header mentions something (Qt types, an include path), it's PUBLIC. If only its .cpp files do, it's PRIVATE.

MODULE 04~1 week

Qt's object model

Goals
  • Write a QObject subclass with your own signals and slots.
  • Explain the event loop and why you must never block it.
  • Use parent–child ownership and know when Qt deletes objects for you.

Qt adds three ideas on top of C++: objects that can talk to each other without knowing each other's type (signals and slots), an event loop that delivers clicks, timers and network data, and object trees that clean up after themselves.

Signals and slots

cpp · counter.h
#pragma once
#include <QObject>

class Counter : public QObject {
    Q_OBJECT                                // needed for signals/slots: see "moc" below
public:
    explicit Counter(QObject *parent = nullptr) : QObject(parent) {}
    int value() const { return m_value; }

public slots:
    void increment()
    {
        ++m_value;
        emit valueChanged(m_value);         // "emit" is just a marker; this calls the signal
    }

signals:
    void valueChanged(int newValue);        // declared, never implemented by you

private:
    int m_value = 0;
};
cpp · main.cpp
#include <QCoreApplication>
#include <QDebug>
#include <QTimer>
#include "counter.h"

int main(int argc, char *argv[])
{
    QCoreApplication app(argc, argv);

    Counter counter;
    QTimer timer;
    QObject::connect(&timer, &QTimer::timeout, &counter, &Counter::increment);
    QObject::connect(&counter, &Counter::valueChanged, [&](int v) {
        qDebug() << "tick" << v;
        if (v == 5)
            app.quit();
    });
    timer.start(500);                       // fire every 500 ms

    return app.exec();                      // the event loop runs until quit()
}

Counter doesn't know a timer drives it, and doesn't know who listens. That decoupling is what lets Ferry's network services stay ignorant of the windows that display them.

The event loop

app.exec() is a loop: wait for something to happen (mouse, key, timer, bytes on a socket), deliver it to the object it belongs to, repeat. Your code runs inside those deliveries. If a slot takes 5 seconds, nothing else happens for 5 seconds: the window doesn't repaint and the OS marks it “Not responding”.

Rule

Never sleep, busy-wait or do long blocking work on the GUI thread. Use timers, Qt's asynchronous APIs (networking is asynchronous by design), or a worker thread (Module 07).

Object trees: who deletes what

Give a QObject a parent and the parent deletes it when the parent is destroyed. That's why Qt code is full of new with no matching delete:

cpp
auto *window = new QWidget;                      // top-level: you own it (or create it on the stack)
auto *button = new QPushButton("OK", window);    // owned by window
auto *layout = new QVBoxLayout(window);          // owned by window
layout->addWidget(button);                       // re-parents into the layout's widget anyway

// Objects that should die "soon but not now" (e.g. inside one of their own signals):
reply->deleteLater();                            // deleted when control returns to the event loop

moc, and the “vtable” error

Q_OBJECT makes Qt's Meta-Object Compiler (moc) generate an extra .cpp containing the signal implementations and type information. With qt_standard_project_setup(), CMake's AUTOMOC runs moc for you. If moc doesn't run on a class (header not listed in the target, or Q_OBJECT added without re-running CMake), the link fails with undefined reference to `vtable for Counter'. Re-run CMake and make sure the header is in the target.

Try it
  1. Build the counter. Add a second listener lambda; then disconnect the first after three ticks (connect returns a QMetaObject::Connection).
  2. Add a signal reachedLimit() emitted at 10, and connect it to QCoreApplication::quit.
  3. Put QThread::sleep(3) in the lambda and watch the ticks bunch up. That's a blocked event loop.
A lambda connected to a network reply captures a QLabel *label. The user closes the window before the reply arrives. What happens, and how do you prevent it?

The label is deleted with its window, then the lambda runs and uses a dangling pointer: a crash. Pass a context object as the third argument: connect(reply, &QNetworkReply::finished, label, [label]{ … }). Qt automatically disconnects when the context object is destroyed. Alternatively hold a QPointer<QLabel> and check it.

Building GUIs with Qt Widgets

Goals

  • Draw your own widgets with QPainter.

A complete small app

cpp · main.cpp
#include <QApplication>
#include <QLabel>
#include <QLineEdit>
#include <QPushButton>
#include <QVBoxLayout>
#include <QWidget>

int main(int argc, char *argv[])
{
    QApplication app(argc, argv);

    QWidget window;
    window.setWindowTitle("Greeter");

    auto *layout = new QVBoxLayout(&window);
    auto *name = new QLineEdit;
    name->setPlaceholderText("Your name");
    auto *button = new QPushButton("Greet");
    auto *output = new QLabel;
    layout->addWidget(name);
    layout->addWidget(button);
    layout->addWidget(output);

    auto greet = [=] { output->setText("Hello, " + name->text() + "!"); };
    QObject::connect(button, &QPushButton::clicked, greet);
    QObject::connect(name, &QLineEdit::returnPressed, greet);

    window.resize(320, 140);
    window.show();
    return app.exec();
}

Layouts, not coordinates

Never position widgets with fixed pixel coordinates. Layouts (QVBoxLayout, QHBoxLayout, QGridLayout, QFormLayout) resize everything correctly on any screen, DPI and language. Nest them for structure; use addStretch() to push things apart, and size policies to say whether a widget wants to grow.

Structure: one class per screen

Past the first exercise, give each window or page its own class, with child widgets as members and signals to report what the user did. Ferry's SendPage emits sendRequested(device) and lets MainWindow decide what happens. The page never talks to the network directly.

cpp · NotePage.h
#pragma once
#include <QWidget>
class QListWidget;
class QLineEdit;

class NotePage : public QWidget {
    Q_OBJECT
public:
    explicit NotePage(QWidget *parent = nullptr);
    void setNotes(const QStringList &notes);

signals:
    void noteAdded(const QString &text);    // the page reports; someone else stores

private:
    QListWidget *m_list;
    QLineEdit *m_input;
};

Forward-declaring class QListWidget; in the header instead of including it keeps compile times down: only the .cpp needs the full header.

Custom painting

When no standard widget looks right, subclass QWidget and override paintEvent. Ferry's pulsing receive beacon and toggle switch are drawn this way (desktop/src/ui/Widgets.cpp).

cpp
class Gauge : public QWidget {
public:
    void setValue(double v) { m_value = std::clamp(v, 0.0, 1.0); update(); }   // update() = repaint soon
    QSize sizeHint() const override { return {160, 160}; }

protected:
    void paintEvent(QPaintEvent *) override
    {
        QPainter p(this);
        p.setRenderHint(QPainter::Antialiasing);
        const QRectF r = QRectF(rect()).adjusted(10, 10, -10, -10);
        p.setPen(QPen(palette().mid().color(), 10, Qt::SolidLine, Qt::RoundCap));
        p.drawArc(r, 225 * 16, -270 * 16);                        // angles in 1/16 degree
        p.setPen(QPen(palette().highlight().color(), 10, Qt::SolidLine, Qt::RoundCap));
        p.drawArc(r, 225 * 16, int(-270 * 16 * m_value));
        p.setPen(palette().text().color());
        p.drawText(rect(), Qt::AlignCenter, QString::number(int(m_value * 100)) + "%");
    }

private:
    double m_value = 0.0;
};

Styling

Qt Style Sheets (QSS) use CSS-like syntax. Combine them with dynamic properties to create variants without subclassing:

cpp
app.setStyle("Fusion");            // same look on every OS, fully stylable
app.setStyleSheet(R"(
    QPushButton { border: 1px solid #D9DCD3; border-radius: 8px; padding: 7px 16px; }
    QPushButton:hover { background: #F1F3F6; }
    QPushButton[primary="true"] { background: #2346B0; color: white; border: none; }
)");
saveButton->setProperty("primary", true);

For dark mode, ask QGuiApplication::styleHints()->colorScheme() and listen to its colorSchemeChanged signal, then swap the palette and style sheet. Ferry's Theme.cpp builds its whole style sheet from named colour tokens so both themes stay consistent.

Designer, QML, and other choices

Qt Creator's Designer lets you draw forms visually (.ui files); CMake's AUTOUIC compiles them. It's great for settings dialogs and forms. Qt Quick/QML is Qt's other UI technology, declarative and animation-friendly, and better for touch and fluid designs; your logic stays in C++. Learn Widgets first: it teaches the underlying model, and it's what Ferry uses.

  2. Write Gauge, drive it from a QSlider, and make it animate smoothly with QVariantAnimation.

You change a label's text in a loop 1,000 times but only see the last value. Why?

Painting happens when control returns to the event loop. Your loop never returns, so Qt paints once at the end. To show progress, do the work in steps driven by a QTimer, or in a worker thread that emits progress signals.

Files and JSON

cpp
#include <QFile>
#include <QJsonArray>
#include <QJsonDocument>
#include <QJsonObject>

bool saveNotes(const QString &path, const QStringList &notes)
{
    QJsonArray array;
    for (const QString &n : notes)
        array.append(n);
    QFile file(path);
    if (!file.open(QIODevice::WriteOnly))
        return false;                                       // file.errorString() says why
    file.write(QJsonDocument(QJsonObject{{"version", 1}, {"notes", array}}).toJson());
    return true;                                            // QFile closes in its destructor (RAII)
}

QStringList loadNotes(const QString &path)
{
    QFile file(path);
    if (!file.open(QIODevice::ReadOnly))
        return {};
    const QJsonObject root = QJsonDocument::fromJson(file.readAll()).object();
    QStringList notes;
    for (const QJsonValue &v : root.value("notes").toArray())
        notes << v.toString();
    return notes;
}

Where to save: QStandardPaths::writableLocation(QStandardPaths::AppDataLocation) gives the right per-user folder on each OS. For settings, QSettings uses the registry on Windows and a .plist on macOS automatically.

TCP: an echo server

cpp
QTcpServer server;
QObject::connect(&server, &QTcpServer::newConnection, [&server] {
    while (QTcpSocket *socket = server.nextPendingConnection()) {
        QObject::connect(socket, &QTcpSocket::readyRead, socket,
                         [socket] { socket->write(socket->readAll()); });   // echo back
        QObject::connect(socket, &QTcpSocket::disconnected, socket, &QObject::deleteLater);
    }
});
if (!server.listen(QHostAddress::Any, 5000))
    qWarning() << "listen failed:" << server.errorString();

Test it with curl telnet://127.0.0.1:5000 and type something. Link Qt6::Network. Note there is no loop of your own and no blocking recv: data arrives through readyRead whenever it comes, possibly split into several pieces. Always buffer and parse; never assume one readyRead is one message.

Firewall

Listening on QHostAddress::Any makes Windows Firewall ask permission the first time. For local experiments, listen on QHostAddress::LocalHost: loopback needs no permission.

UDP: shouting to the whole network

cpp
QUdpSocket udp;
udp.bind(QHostAddress::AnyIPv4, 45454, QUdpSocket::ShareAddress | QUdpSocket::ReuseAddressHint);
udp.joinMulticastGroup(QHostAddress("239.255.0.1"));
QObject::connect(&udp, &QUdpSocket::readyRead, [&udp] {
    while (udp.hasPendingDatagrams()) {
        const QNetworkDatagram d = udp.receiveDatagram();
        qDebug() << d.senderAddress() << d.data();
    }
});
udp.writeDatagram("hello?", QHostAddress("239.255.0.1"), 45454);

HTTP

As a client, use QNetworkAccessManager. Every request is asynchronous and returns a QNetworkReply:

auto *nam = new QNetworkAccessManager(&app);

Your TCP client sends a 10 KB JSON message, but the server's JSON parser fails half the time. Why?

TCP is a byte stream, not a message stream. The 10 KB can arrive in several readyRead calls. Frame your messages, for example with a length prefix or a newline terminator, accumulate bytes in a buffer, and only parse when a whole message has arrived.

Threads without freezing

Goals
  • Know when you need a thread and when the event loop is enough.
  • Run CPU-heavy work on a worker and report progress back to the GUI safely.

Networking and timers don't need threads in Qt; they're asynchronous already. You need a thread for work that keeps the CPU or disk busy for more than ~50 ms: hashing a large file, image processing, parsing a big log, number crunching.

The one rule

Only the main (GUI) thread may touch widgets. Workers communicate with the GUI through signals. Qt then delivers them as queued calls on the receiver's thread automatically.

The quick way: QtConcurrent

cpp
#include <QtConcurrent>      // link Qt6::Concurrent (installed on your PC)

auto *watcher = new QFutureWatcher<QByteArray>(this);
connect(watcher, &QFutureWatcher<QByteArray>::finished, this, [this, watcher] {
    m_hashLabel->setText(QString::fromLatin1(watcher->result().toHex()));   // back on GUI thread
    watcher->deleteLater();
});
watcher->setFuture(QtConcurrent::run([path] {                                // runs on a pool thread
    QFile f(path);
    QCryptographicHash h(QCryptographicHash::Sha256);
    if (f.open(QIODevice::ReadOnly))
        h.addData(&f);
    return h.result();
}));

The long-lived way: a worker object

cpp
class Hasher : public QObject {
    Q_OBJECT
public slots:
    void hash(const QString &path)              // runs on the worker thread
    {
        QFile f(path);
        if (!f.open(QIODevice::ReadOnly)) {
            emit failed(path);
            return;
        }
        QCryptographicHash h(QCryptographicHash::Sha256);
        qint64 done = 0;
        while (!f.atEnd()) {
            const QByteArray chunk = f.read(1 << 20);
            h.addData(chunk);
            done += chunk.size();
            emit progress(done, f.size());      // queued to the GUI thread
        }
        emit finished(path, h.result().toHex());
    }
signals:
    void progress(qint64 done, qint64 total);
    void finished(const QString &path, const QByteArray &hex);
    void failed(const QString &path);
};

// In MainWindow's constructor:
m_thread = new QThread(this);
auto *worker = new Hasher;                       // no parent: it will live on another thread
worker->moveToThread(m_thread);
connect(m_thread, &QThread::finished, worker, &QObject::deleteLater);
connect(this, &MainWindow::hashRequested, worker, &Hasher::hash);
connect(worker, &Hasher::progress, this, &MainWindow::showProgress);
m_thread->start();

// In MainWindow's destructor:
m_thread->quit();
m_thread->wait();

If two threads touch the same plain data (not through signals), protect it with QMutex/std::mutex and QMutexLocker/std::lock_guard, or use std::atomic for single counters. Ferry's iOS code does the same with a small lock-protected Locked<T> box.

Try it
  1. Build a “File Fingerprint” app: drop a file on the window, show a progress bar while a worker computes its SHA-256, then show the hash with a Copy button. The window must stay responsive (try dragging it) while hashing a 4 GB file.
  2. Add a Cancel button. Hint: a std::atomic<bool> the worker checks every chunk.
Why does worker have no parent before moveToThread?

An object can only be moved to another thread if it has no parent; children always live on their parent's thread. Ownership is handled instead by connecting QThread::finished to deleteLater.

Interfaces between your own modules

Goals
  • Split an app into layers that depend in one direction only.
  • Define an interface as an abstract class and code against it.

Apps stay easy to change when the parts talk through narrow, explicit interfaces. Ferry is organised in two layers:

LayerContainsMay include
src/coreProtocol, HTTP server, discovery, send/receive logicQtCore, QtNetwork. Never widgets.
src/uiPages, dialogs, themecore and QtWidgets

Because core never includes a widget, it can be tested without a window (Ferry's integration test does exactly that), and a different UI could reuse it unchanged.

An interface is an abstract class

Ferry's progress dialog shows both sending and receiving. Instead of knowing about two services, it depends on one small interface (desktop/src/core/Transfer.h):

cpp
class TransferSource {
public:
    virtual ~TransferSource() = default;                  // always virtual in an interface
    virtual TransferSnapshot snapshot() const = 0;        // "= 0": must be implemented
    virtual void cancelTransfer() = 0;
};

class SendService : public QObject, public TransferSource { /* implements both */ };
class ReceiveService : public QObject, public TransferSource { /* … */ };

TransferDialog::TransferDialog(TransferSource *source, bool incoming, QWidget *parent);   // takes either

The same pattern lets you swap a real device for a fake one in tests. Ferry's UI snapshot tool feeds the dialog a FakeTransfer to render a mid-transfer screen without any network.

Guidelines

  • Headers are contracts. Keep them small; put includes and helpers in the .cpp. Anything in a header becomes something callers can depend on.
  • Pass data, not objects, across layers: plain structs such as Ferry's TransferSnapshot or DeviceInfo.
  • Report upward with signals, call downward with functions. The UI calls send(); the service emits finished().
  • One reason to change per class. If a class both parses HTTP and decides when to show a dialog, split it.

Interfacing with the OS, hardware and other languages

Goals
  • Call Win32, POSIX and macOS APIs from C++, and link the right system libraries.
  • Talk to a microcontroller over a USB serial port.
  • Expose C++ code through a C API so Python, Swift or C# can call it.

Platform-specific code

Qt covers most needs, but sometimes you call the OS directly. Guard each platform's code and keep it in small, isolated functions behind a common header:

cpp · Power.cpp
#include "Power.h"            // declares: bool isOnBattery();

#if defined(Q_OS_WIN)
#include <windows.h>

bool isOnBattery()
{
    SYSTEM_POWER_STATUS s;
    return GetSystemPowerStatus(&s) && s.ACLineStatus == 0;   // kernel32: linked by default
}

#elif defined(Q_OS_MACOS)
#include <IOKit/ps/IOPowerSources.h>    // CMake: target_link_libraries(app PRIVATE "-framework IOKit" "-framework CoreFoundation")

bool isOnBattery()
{
    CFTypeRef info = IOPSCopyPowerSourcesInfo();
    if (!info)
        return false;
    CFStringRef type = IOPSGetProvidingPowerSourceType(info);
    const bool battery = type && CFStringCompare(type, CFSTR(kIOPSBatteryPowerValue), 0) == kCFCompareEqualTo;
    CFRelease(info);                       // C APIs: you release what you "Copy"
    return battery;
}

#else
bool isOnBattery() { return false; }
#endif

Ferry uses this exact technique to tell a MacBook from a desktop Mac (desktop/src/core/AppSettings.cpp). The Win32 docs on learn.microsoft.com list the header and library for every function. If the library isn't linked by default (for example ws2_32, iphlpapi), add it to target_link_libraries.

On macOS you can also mix Objective-C into C++ by naming a file .mm (Objective-C++). That gives you any Cocoa API:

objective-c++ · MacInfo.mm
#import <Foundation/Foundation.h>
#include "MacInfo.h"           // declares: std::string macOSVersion();

std::string macOSVersion()
{
    @autoreleasepool {
        return [[[NSProcessInfo processInfo] operatingSystemVersionString] UTF8String];
    }
}
// CMake: project(App LANGUAGES CXX OBJCXX) and add MacInfo.mm to the target inside if(APPLE)

Hardware: a serial port to an Arduino

An Arduino, ESP32 or PIC with a USB-UART shows up as a COM port (COM3) on Windows and /dev/cu.usbmodem… on macOS. Qt Serial Port makes it look like any other QIODevice. It's not installed on your PC yet: open Qt Maintenance Tool › Add or remove components › Qt 6.11.1 › Additional Libraries › Qt Serial Port.

cpp
#include <QSerialPort>           // CMake: find_package(Qt6 COMPONENTS SerialPort), link Qt6::SerialPort
#include <QSerialPortInfo>

for (const QSerialPortInfo &info : QSerialPortInfo::availablePorts())
    qDebug() << info.portName() << info.description() << Qt::hex << info.vendorIdentifier();

auto *port = new QSerialPort("COM3", this);
port->setBaudRate(QSerialPort::Baud115200);    // must match Serial.begin(115200) on the board
if (!port->open(QIODevice::ReadWrite)) {
    qWarning() << port->errorString();          // e.g. "Access is denied": Arduino IDE's monitor has it open
    return;
}

connect(port, &QSerialPort::readyRead, this, [this, port] {
    m_buffer += port->readAll();                  // bytes arrive in arbitrary pieces...
    qsizetype nl;
    while ((nl = m_buffer.indexOf('\n')) >= 0) {  // ...so split into lines yourself
        const QByteArray line = m_buffer.left(nl).trimmed();
        m_buffer.remove(0, nl + 1);
        handleLine(QString::fromUtf8(line));      // e.g. "T=23.5"
    }
});
port->write("LED 1\n");

The matching Arduino sketch prints Serial.println(value) and reads commands with Serial.readStringUntil('\n'). Combine this with Qt Charts (installed) to plot sensor data live: a good project for an electronics engineer.

Being called from other languages: the C ABI

Almost every language can call C functions in a DLL. None can reliably call C++ directly, because of name mangling, classes and exceptions. So you wrap your C++ library in a thin C layer:

cpp · counter_c.h
#pragma once

#if defined(_WIN32)
#  define COUNTER_API __declspec(dllexport)
#else
#  define COUNTER_API __attribute__((visibility("default")))
#endif

#ifdef __cplusplus
extern "C" {                       // no name mangling: the symbol is exactly "counter_new"
#endif

typedef struct Counter Counter;    // opaque handle: callers never see inside

COUNTER_API Counter *counter_new(void);
COUNTER_API void counter_add(Counter *c, int amount);
COUNTER_API int counter_value(const Counter *c);
COUNTER_API void counter_free(Counter *c);

#ifdef __cplusplus
}
#endif
cpp · counter_c.cpp
#include "counter_c.h"
#include <vector>

struct Counter {                    // the real C++ lives here
    std::vector<int> history;
    int value = 0;
};

Counter *counter_new(void) { return new Counter; }
void counter_add(Counter *c, int amount) { c->value += amount; c->history.push_back(amount); }
int counter_value(const Counter *c) { return c->value; }
void counter_free(Counter *c) { delete c; }
// Never let a C++ exception cross this boundary: catch inside and return an error code.
cmake
add_library(counter SHARED counter_c.cpp)    # -> counter.dll / libcounter.dylib
python · use_counter.py
import ctypes

lib = ctypes.CDLL("./build/libcounter.dll")   # MinGW names it libcounter.dll; macOS: libcounter.dylib
lib.counter_new.restype = ctypes.c_void_p
lib.counter_add.argtypes = [ctypes.c_void_p, ctypes.c_int]
lib.counter_value.argtypes = [ctypes.c_void_p]
lib.counter_free.argtypes = [ctypes.c_void_p]

c = lib.counter_new()
lib.counter_add(c, 40)
lib.counter_add(c, 2)
print(lib.counter_value(c))   # 42
lib.counter_free(c)

Swift imports the same header through a bridging header or module map, and since Swift 5.9 can even call many C++ APIs directly with C++ interoperability turned on. C# uses [DllImport]. The C header is the universal adapter. Check the exports with nm -D (Linux), objdump -p libcounter.dll (MinGW) or nm -gU (macOS).

Your serial app works, but sometimes reads a half line like T=2. What's wrong?

Serial data, like TCP, arrives in arbitrary chunks. You parsed each readyRead chunk as a complete message. Accumulate into a buffer and only process complete lines, as in the example.

The debugger

Build in Debug mode (-DCMAKE_BUILD_TYPE=Debug, or the Debug kit in Qt Creator) and press F5. Click left of a line number for a breakpoint; F10 steps over, F11 steps into, Shift+F11 steps out. When a program crashes under the debugger, it stops on the crashing line and the call stack shows how you got there. That's the single most useful view.

The same from a terminal with gdb (on macOS, lldb uses nearly identical commands):

Cheap but effective: qDebug() << "state" << value; prints any Qt type readably.
